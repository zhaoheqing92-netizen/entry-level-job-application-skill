# 初级岗位求职助手｜第一轮产品与获客讨论

2026-11-19 · 供设计师与作者决策

**建议先让一个正在看校招岗位的人，拿自己收藏的一条官网职位和两句经历，判断值不值得继续。** 他应当能看见一条有出处的理由、一个仍需核实的条件，以及自己接下来能做什么。这件事用现有技能就能做，也容易请本人指出哪一步有用。扩大宣传前，先解决教程会多要简历、草稿话术会授权上传这两处问题。

免费入口旁可以直接放这句话：

> 使用 entry-level-job-application。这个官网岗位是【链接】。我【毕业届别、专业】，做过【一项相关经历】。请核对实际工作地和硬性资格，引用一条岗位原文，告诉我该继续、先问哪一项，还是跳过。只核岗位，不注册、不上传、不提交。官网读不到时告诉我，我可以贴出职位说明。

读者也应在下载前看到一次判断长什么样。现有**离线虚构案例**中，同一位 2025 届工程本科生只考虑深圳，做过传热试验数据整理。Alpha 的助理测试岗与这段经历相关，岗位未限定毕业年份，值得继续了解仪器维护要求；Beta 的热管理研发岗虽然名称更贴近目标，却明确限定 2027 届硕士，可以直接跳过。这两行就能展示核对条件省去了哪次无效准备。[原始岗位摘录](../tests/scenarios/quick-search.md) · [留档输出](../evaluation/forward-test.md)

## 一、从第一次打开到决定申请，哪里最容易出问题

按误操作的后果、阻断首用的程度、随后能否补救排序。下列“可能”描述走读发现的风险，眼下还没有用户流失数据。

| 顺序 | 用户遇到什么 | 证据、影响与处理 |
|---|---|---|
| 1 | 选了“先给我看，不提交”，生成的话却允许向招聘方上传附件 | 我们分别运行了教程源码和下载包中的话术函数。默认选草稿、附件栏留空时，两者都显示“当前：只填草稿，等你确认”，同时生成“只填写草稿和上传上述附件，给我检查，不提交”。空栏留下附件占位符；填入“中文简历”就会把这份文件带入上传授权。网页只生成文字，实际风险发生在用户把它发给能操作招聘网站的 Agent 后。README 的草稿示例明确禁止上传，现有浏览器测试对默认草稿只断言含“不提交”。[教程](../docs/starter-kit/guide.html) · [浏览器测试](../tools/test_guide.cjs) · [中文 README](../README.md) |
| 2 | 下载成功，第一句却发不出去，或先被索取完整简历 | 完整包需要解压并由支持技能的 Agent 加载。手机能扫码，普通聊天窗口未必能加载本地技能。教程和一页 PDF 示范 Codex 的 `~/.agents/skills/`，客户端参考还举了 `~/.codex/skills/`；两者都有适用背景，却把判断留给新人。教程默认打开“找岗位”，简历栏写着可稍后提供，留空生成的话术却要求先向用户索取简历。技能正文原本允许只说学历、经历、方向。先让用户在自己的客户端确认已读到该技能，再用一个职位和最少事实出结果。[客户端参考](../skills/entry-level-job-application/references/clients.md) · [教程与速查单](../docs/starter-kit/README.md) · [首次使用说明](../skills/entry-level-job-application/SKILL.md) |
| 3 | 用户来找热管理岗位，第一轮可能只得到聚合页和“待核” | 11 月 10 日的四次真实博查查询返回 20 条，其中 18 条来自第三方。杭州短查询的五条摘要都明显跑题，企业域名也可能指向产品页。试用先给“核对我手上这一条”的入口；想发现新岗的人仍可选搜索。原页读不到就标“未核实”，核实后因届别不合而排除也有价值。记录两种入口各自能否帮用户作决定，搜索返回条数没有这个解释力。[搜索报告与限制](../evaluation/search-quality-2026-11-10.md) · [筛选口径](../skills/entry-level-job-application/references/scoring.md) |
| 4 | 已经手投过多家的人，会高估“记住进度”的范围 | SQLite 台账靠同一私有数据库和稳定的候选人、雇主、岗位、批次标识防重复。台账保存状态、时间、备注和证据引用，提交时实际用的那一版简历还要由 Agent 单独保存在私有目录。作者自用时先拿一个手投过的岗位对照官网历史；若换台电脑、换一份记录就显示“新岗位”，仍需核查。提交超时要先查对应账户与岗位的回执；缺少可靠私有记录时可继续准备文案。[执行与恢复](../skills/entry-level-job-application/references/execution.md) · [状态表实现](../skills/entry-level-job-application/scripts/application_state.py) · [并发测试](../tests/test_application_state.py) |
| 5 | 用户看见“通过”，很难知道哪些是工具查过的 | `check_application.py` 可检查证据记录的一致性、附件用途和授权；官网原文、文件正文、表单全貌仍靠宿主实际读取。已有离线任务确实发现了名为 `latest.pdf` 的求职信被旧索引当成简历，这是值得展示的信任点。每个结果旁给一小段实际依据，并区分“本地草稿”“官网已保存”“提交结果未知”“官网已确认”。遇到本人验证或测评，指明接手动作；“继续”本身无法证明页面已通过。[证据约定](../skills/entry-level-job-application/references/evidence.md) · [附件实测记录](../evaluation/competitive-forward-test.md) · [账号交接](../skills/entry-level-job-application/references/accounts-and-recovery.md) |
| 6 | “官方”容易让人误判数据交给谁 | “只走官网”指雇主及它链接的招聘系统；验证码参考里说的“官方服务”指另一家服务供应商，涉及不同的数据接收方、授权与费用。教程的申请话术已经选择“验证码交给我”。保留这一选择并在交接时说清由谁操作；首次核岗和本地写文案都用不到登录或验证服务。[验证码参考](../skills/entry-level-job-application/references/captcha.md) · [交付包授权话术](../docs/starter-kit/prompts/02-authorized-apply.txt) |

**下载包已经解决了一部分交付问题。** 本轮直接读 ZIP 目录并校验完整性。教程目录中的技能 ZIP 有 14 个文件；README 主推的客户包有 24 个，根部能看到 `SKILL.md`、`guide.html` 和 `先看这里.txt`，没有嵌套 ZIP。两个包的技能文件与当前源码一致，包的 SHA-256 与 11 月 10 日记录相符。客户包里的教程仍含前两项指出的话术；仓库有虚构候选人样例，客户包里没有这份样例，离线演示也在仓库侧。应先把一组可直接理解的输入和结果放到第一次看得到的地方。线上商品当前交付哪一版，仍需作者从领取端核对。[客户包](../downloads/entry-level-job-application-with-guide.zip) · [打包清单](../tools/package_skill.py) · [历史包指纹](../evaluation/search-quality-artifacts.json)

## 三、优化清单与成本

以下工时按一人、已有兼容环境估算，新增现金预算为零。今晚若只有一小时，先做 A1 和 A2，让读者拿到能直接用的“仅核岗”指令；修正草稿话术并验包后，再让作者发布新版本。

|---|---|---|---|
| A1 今晚 · 设计师 | 在中英文 README 及“先看这里”的免费入口给出首段的核岗指令；另给一句“只在本地写草稿，不访问招聘表单、不上传附件”。当前教程默认草稿涉及上传，在相邻说明中写明。把扫码支持移到结果之后，保留同版同权、宿主及模型费用说明，英文页标明教程为中文。 | 现有版本就有一条权限清楚的试用路径；手机读者也能在下载前判断能否使用。 | 20–25 分钟 |
| A2 今晚 · 设计师 | 11 月 8 日参赛笔记已经有四分钟分镜，先取其中的资格判断一幕。用首段的 Alpha、Beta 和两句依据排一张手机可读的图，文字版随图。角标明示“离线虚构示例”。 | 免费页、Release、SkillPay 可共用同一份演示材料，读者在下载前就能判断是否值得试。 | 25–35 分钟 |
| A3 今晚 · 工程师 | 在安装说明里注明解压后哪一层应直接看到 `SKILL.md`，复用教程已有的“确认能发现并读取技能”指令。用 `tools/package_skill.py --with-guide` 和新输出名准备本地候选包，核 ZIP 根目录、相对链接、话术和 SHA-256，拟好版本说明；C1 修好后再封版。 | 能定位“领到包却没加载”卡在哪一层，也便于作者比对平台实际交付。 | 25–35 分钟 |

## 四、怎样拿到前 10 个真实用户

**把获客目标定为 10 位外部求职者；作者另记为第 1 号自用案例。** 一位求职者在自己的兼容 Agent 中，针对实际要找的工作跑一次，并能指出对具体岗位或草稿做了什么决定，计 1 人；有依据地放弃一个岗也算。同一人跨平台只计一次，标明独立完成或有人陪同。中途卡住的计入尝试分母。付费支持、下载、报名各自记录。

按预计每投入一分钟作者时间能得到多少次有效试用排序。表中是每轮可尝试的招募规模和容量估算，无历史转化率；各渠道可能重复，也可能全部为零。先走前两条，人数不足再往下走。

| 优先 | 渠道与具体动作 | 作者 effort／预期 yield | 何时停或调整 |
|---|---|---|---|
| 1 | 正在互相讨论校招岗位的同学或实验室伙伴。只在已有一对一对话中找 3 位手上有具体职位、已有兼容客户端的人，各邀请一次。让对方用自己的设备，作者只观察卡点。 | 约 30 分钟；一轮安排 1–2 位完成，合适时在下一周对另一小组重复。 | 两人都卡在安装就暂停邀新；问清哪一步，回到 C2。 |
| 2 | 同伴转介。一次试用结束后，只问愿意者能否把同一条免费指令转给一名正在挑岗位的同学；新同学主动报名，再接洽。 | 每轮约 10–15 分钟；3 次自愿转介预计 0–2 位新用户，尤其适合安排独立试用。 | 无回复即止；不索要名单，不用好评、返现或转发作交换。 |
| 3 | 院系就业互助群或校园技术社团。先征得管理员同意，选一个原本就交流校招或 Agent 工具的群，发一次 3 个名额的“自带官网岗位核对”时段。参与者在本机执行，20 分钟一起答疑。 | 含协调约 30–40 分钟；一场预计 1–3 位，先记自愿报名者，再记实际完成者。 | 无人报名就问管理员受众是否合适；不复制到一串群里。 |
| 4 | GitHub 与 SkillPay 的现有访客。在上手说明末尾留一个可选问题“你停在哪一步？”，GitHub 可用已有 Issues 收无个人资料的复现，SkillPay 走平台已有反馈渠道。 | 随 B1 增加约 5–10 分钟，一周预计 0–1 位可确认的新用户；访问量未知。 | 没有反馈就记未知；不给下载者或买家逐个发消息。 |
| 5 | 小红书。已有一次泛宣传无效果。等有可公开的作者自用结论，再发一次具体复盘，如“我用一条热管理校招 JD 核对了什么”。声明作者身份，展示一次纠正，站内回答实际问题。 | 复用已有材料约 25–40 分钟，一篇预计 0–1 位可确认用户，优先级最低。 | 按发帖当日账号规则决定能用的入口；不附支付码，不用谐音或私信口令导流。无真实试用线索就暂停。 |

**可直接使用的邀请。** “你上次提到有个校招岗位拿不准届别。我做了个免费的 Agent 技能。你愿意用自己的客户端和那条官网链接试一次吗？两句背景就够，只核对岗位，不上传简历、不投递。我想知道你最后怎么选，以及哪一步需要我解释。卡住也算反馈。”

第一周争取作者自用一次、熟人独立或陪同完成 2 次。外部十席按**熟人 4、同伴转介 3、获准小组 3**安排；转介可分两轮，小红书和平台自然访问不承担保底人数。每周给对外试用留两个半小时时段；若某渠道已有完成者且还有志愿者，下周重复一次。若有报名却普遍卡在加载，先解决加载问题；若一人都没开始，先了解对方手上是否真有要核的岗位和能用的客户端。

只需在现有私有笔记记匿名编号、渠道、宿主，以及“开始尝试 → 加载成功 → 得到有依据的决定”分别到了哪一步。记用户耗时、作者协助分钟和具体卡点；每个渠道分别报“完成人数／尝试人数”，零完成就保留零。结束时问“哪一条你会采纳？哪一步还得自己重做？”一周后只向同意者回访是否用于第二个岗。负面反馈有同等价值，公开引语另征本人同意。

### 单独评估作者自用并公开全过程

作者的热管理／冷却方向能直接检验三个难点：实际工作地、2027 届资格、历史已投去重。用下一次自然发生的求职任务，先在私下记录原本想解决的问题、实际耗时、Agent 的判断、本人对官网原文的纠正、最后采取的动作。若原计划就要申请，可按自己原有节奏继续，记录由谁提交、官网确认到哪一步。一次明智的弃投或只拿到草稿也可以写完。这样能回答“这个人在这个任务上用到了什么”，仍需外部新人检验安装和独立使用。

**公开过程可以完整，公开材料必须最少。** 以文字复盘“输入了哪些非敏感条件 → 核了哪条要求 → 人纠正了什么 → 最后决定”。原简历、登录画面、邮箱、回执号、带令牌的链接和本地路径留在私有设备。企业、岗位编号、学校与项目细节组合也可能让招聘方反推本人；在招岗位必要时延后发表，只写岗位类别和判断依据，配图用标明“虚构重绘”的素材。没有同意就不用他人的截图、引语或评价。[技能的私有资料边界](../skills/entry-level-job-application/references/intake-and-privacy.md)

额外记录限 10 分钟，可公开的整理限 20 分钟。临近截止、对账号操作没把握、公开会影响招聘沟通时，优先按原方式求职，复盘可以只留私下。不要为了录屏重投、为了凑故事投本来不想投的公司，也不要用一次面试或拒信推断产品效果。

## 五、本机技能可用性与产出

以下名称已在 `~/.codex/skills/` 核对。按实际适用阶段选用，首轮的渠道比较只借用时间成本和用户质量这两个问题。

| 技能 | 在项目中如何使用、会得到什么 |
|---|---|
| `positioning-statement` | 现在可用。输入“已有兼容 Agent、正在选校招岗位、手上有官网链接”，与手动逐页核对比较，得到一句 README 定位和一个能当场核对的承诺。用首批试用者能否复述“需要准备什么、能拿回什么”检验。 |
| `discovery-interview-prep` | 招首批用户前可用。围绕“上一个被你放弃的岗位”和“拿到这次输出后做了什么”生成 10 分钟观察提纲，留下用户实际动作、停顿和纠正，避免问“是不是很好用”。 |
| `organic-growth-advisor` | 暂缓。它的适用前提是已有相对明确的客户与产品价值。等出现外部用户第二次自发使用，再比较“在同一院系换触达渠道”和“拓展到新专业”两条路，交付一个优先方向及验证动作。 |
| `acquisition-channel-advisor` | 完整模型适用于已有渠道数据的经济性比较。本品零反馈且付费为自愿支持，当前只做“作者分钟／真实完成者、是否用于第二岗”的渠道表；有分母后再比较。先不估算终身价值或回本期。 |
| `voice-of-customer-miner` | 从已有竞品 issue 提取少量可追溯的原话、日期、上下文和待验证问题，产出“别人曾遇到什么／我们的用户是否也遇到”的假设表。首批本品反馈另开一列，经同意再摘录。 |
| `skill-quality-reviewer` | 下一开发轮只取相关检查项，对照技能触发说明、教程生成的话术、参考文件和包内入口，形成带文件位置、触发条件和验收例的改进计划。文档结构评分无法证明求职者能完成任务。 |
| `skill-improver` | **本轮不用。** 它会依据 reviewer 的改进计划实际修改文件。经作者选择 C1 或 C2 后再执行对应项，交付最小差异和回归结果。重新排版整套技能对前十人试用帮助有限。 |

## 六、仍请设计师裁决的取舍

| 要决定什么 | 建议与可能改变决定的证据 |
|---|---|
| 首屏主打“核手上一岗”还是“帮我发现新岗”？ | 默认前者，因为输入和结论可核对；保留后者的次入口。若外部试用者多数没有可带入的链接，却愿意带方向和城市来搜，调整入口顺序。 |
| 草稿默认能走到哪里？ | 建议本地出稿为默认，另列“官网填草稿”“上传指定文件”。即使有人更看重官网预填，也应让标签和发给 Agent 的授权文字完全一致。 |
| 第一个公开案例要不要展示真实提交？ | 默认只公开作者同意、对求职无影响的过程摘要。若本人本来就要提交且能脱敏，再写实际状态。招聘流程未结束或组合信息可识别时延后。 |
| 十人如何报，什么时候扩大渠道？ | 对外报告把作者与独立外部用户分开；建议出现两位无需作者协助便能完成任务的外部用户后，再增加公开曝光。若只有作者陪同才成功，优先修上手。 |
| 今晚多做一条视频，还是先修正首用？ | 优先两处话术和静态结果图。等试用者能读懂结果、却说不清怎样从下载走到输出，再为这段操作录 GIF。Discussions 同样等有可持续回答的公开问题再开。 |

本轮阅读了技能正文、八份参考文档、双语 README、教程、评估记录、测试和相邻参赛笔记；查看了预览图及一页 PDF，逐字节比对了两种 ZIP 的运行文件，并在内存中运行了两版教程的搜索及草稿话术函数。40 项测试和 8＋4 个演示场景取自仓库历史记录。真实用户完成率、节省的时间、线上实际交付版本和真实招聘系统的提交结果仍待验证。
