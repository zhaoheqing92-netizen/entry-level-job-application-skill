**对任务书（不是对裁决）的三处实质分歧**

1. **T3 的 "C1-lite" 定级低估了工作量。** 现在不是"改两句字符串"，而是把二选一的 `submit-mode`（`guide.html:46`）改成至少四个授权级别，并保证任意组合不放大。这需要先写状态模型，再改 UI、话术、提示、测试和 PDF；半天只在状态模型已定的前提下成立。按 "lite" 只改字符串，组合放大几乎必然留下。
2. **T1 的"结果之后"和"不删"没有可验收定义。** 现稿已经出现两个信号：支付块停在快速开始之前；重排前的"文档适配不等于逐个客户端实测通过"不见了，现在只剩"实际能力取决于宿主工具、权限和网站"（`README.md:81`，总括的"未验证所有客户端集成"在 `:99`）。前者是顺序问题，后者是证据删除，正好是 T1 明令不许的。
3. **T4 的"验包"不验话术。** 列根目录、无嵌套 ZIP、SHA-256 只能证明"包没坏"，不能证明"包里的默认草稿不再授权上传"。`tools/test_guide.cjs:7` 把根目录硬编码为 `docs/starter-kit`，打包后的 `guide.html` 从来没有被行为测试跑过；而 `package_skill.py:30-43` 恰恰会在打包时改写这个文件。验收必须让同一个 guide 测试能指向解压后的包。

这三条不是反对裁决，是反对把裁决翻译成"改完文件就算完成"。如果任务书只能再加一句验收，我建议加：**对客户包里解压出来的 `guide.html` 跑一遍 `test_guide.cjs`，并对所有随包文本做一次授权短语扫描。**

## 二、两方都漏掉的风险或盲点

### 2.1 T3：话术授权是状态机，不是字符串

我评审开始时 `guide.html` 还是旧版，比讨论里写的更具体：`:46` 只有两个选项，`draft`（先给我看，不提交）和 `submit`（按授权直接提交）；`:96` 无条件生成"允许上传：…"；`:97` 在 draft 分支生成"只填写草稿和上传上述附件"。默认状态同时说了"只填草稿"和"上传上述附件"；`:48` 的帮助语还写着"看到官网回执，才算提交成功"，对本地草稿用户也在暗示一次提交。下面 1–7 先用旧版说明为什么不能只改字符串，再在末尾对照落盘版逐项核一遍。

1. **只改默认句不够，必须删掉"允许上传"整行。** 占位符"【请写明允许上传的附件】"本身就在邀请用户填一个文件名；填了"中文简历"，Agent 就会把这份文件当成已授权。正确做法不是把"上传"改成"不上传"，而是本地草稿分支根本不生成附件行。落盘版把 `upload-field` 藏起来、草稿分支不再拼附件行，方向对了；仍建议在草稿分支把 `allow-files` 真正 `disabled` 并清空，而不是只靠 `hidden`，避免残留值被后续脚本或浏览器恢复读回。
2. **"四个独立选项"不能做成四个正交 checkbox。** 现实里"提交"依赖"官网填写"，"上传"依赖"官网填写"，"上传"还依赖具体文件名。四个独立勾选会产生"只提交不填写""上传但没列文件"这类非法组合，生成的话术要么自相矛盾，要么被迫偷偷补全——后者就是权限放大。建议做成单调层级：L0 只核岗 → L1 本地草稿 → L2 官网填草稿 → L3 上传指定附件 → L4 提交。L4 必须显式包含 L2；L3 必须有非空文件名；未选 L2 时 L3/L4 不可选。这样"独立"体现在每一级都要单独勾选，而不是四个互不相干的开关。
3. **"只填草稿"标签必须先分清本地还是官网。** 旧版的状态语"只填草稿，等你确认"（原 `:48`、`:92`）在中文里两种都说得通。落盘版已改成四个独立标签（`仅在本地写草稿` / `在官网填写草稿` / `上传指定附件` / `最终提交`），这一点修对了。仍缺两处：L2 没有提示"官网会收到已确认字段"——填写草稿不是隐私中性的；L1 只说"进度保存在私有目录"，没说草稿本身存哪里。
4. **帮助语要随选项变。** 本地草稿下显示"看到官网回执才算提交成功"会让用户以为已经投了；上传下显示"验证码和测评由本人处理"是合适的；提交下才该说"以回执为准"。落盘版的 `#apply-status` 已随选项变，但 `guide.html:58` 的帮助语仍是静态一句，不满足"贴着对应选择放"（裁决 3）。
5. **旧测试会放过原 bug，落盘版已加负断言，但还缺几条。** `test_guide.cjs:38` 原来对默认草稿只断言 `/不提交/`，而 bug 文本"只填写草稿和上传上述附件…不提交"正好匹配。落盘版已加 `:53` 的 `doesNotMatch(/上传|中文简历\.pdf/)` 和 `:48` 的空上传断言，这是对的。仍缺：
   - **核岗模式 + 已填附件目录**：`searchPrompt()` 在 check 模式下仍会无条件追加"附件目录：…"（`guide.html:104`），话术后面却写"不上传"。应改成只在 find/材料模式追加；至少加一条断言：check 模式的 `#search-prompt` 不含"附件目录"。
   - **本地草稿的默认文本**：页面加载后、任何交互前就检查一次；用户是可以直接点"复制给 Agent"的。
   - **apply 的复制**：目前只测了 search 的剪贴板和回退；apply 也应测一次，确保复制的就是用户看到的授权文本。
   - **组合泄漏**：把 `allow-files` 填成"中文简历"后依次切到 form/draft，确认两者都不含该文件名；现在只测了 upload→draft 这一条路径。
6. **只测 HTML 不测 Agent 行为。** T3 的输出是给 Agent 的指令；HTML 文本对了，Agent 仍可能按 `references/intake-and-privacy.md:3` 的"先读取用户授权的简历"先要简历。`SKILL.md:20` 说"没有简历也可以先说学历、经历和想做的工作"，但参考文档的默认顺序没有条件句。建议在 T3 验收里加一次新上下文前向测试：用新生成的"空简历"话术＋一条虚构 JD＋两句事实，观察 Agent 是否 (a) 不索要完整简历，(b) 不打开表单、不上传，(c) 给出继续/先问/跳过之一。这是半小时级的离线测试，比再改十句文案更能证明修好了。若不做，至少把 `intake-and-privacy.md:3` 改成"有简历先读简历；没有简历时，用两句事实开始核岗，不为核岗索要完整简历"（这行在 T3 清单外，记录里要标偏离），否则指南和技能正文会互相拉扯。
7. **残留面。** 落盘版已把 `guide.html` 的打印速查段改成新的核岗话术和四选项说明，这一面修好了。仍未同步的是：
   - `prompts/01-search-only.txt:2` 仍以"我的简历在【简历完整路径】"开头。用户没有简历时，这份随包模板直接不可用，和首屏"没有简历也能开始"冲突。
   - `prompts/02-authorized-apply.txt:2` 是显式全授权模板（填写、上传、提交），保留可以；文件名也写了 authorized。但它和默认草稿同处一个包，没有一句"这不是默认，只有你已决定投递时才用"；对非技术用户，"authorized" 不等于"非默认"。
   - `customer-start.txt:27` 已注明"guide.pdf 仍是旧版"；这是诚实的，但标注不等于消除。PDF 是用户会单独打开的一页纸，旧授权文本仍在里面。
   - 仓库版 `docs/starter-kit/先看这里.txt:9` 仍写"读取我的简历"，而客户包用的是 `customer-start.txt`；同一个文件名两个版本，容易在后续维护中拿错。
   这些不是"文档小瑕疵"，它们是同一授权话术的不同发行面。用户完全可能只读 PDF、只复制 01/02、或只看"先看这里"。如果本轮不修，版本说明必须逐条列出"仍未同步"，不能写"已修复"。

**建议的授权层级（供 T3 实现和测试共用）**

| 层级 | 标签（给用户看） | 话术必须包含 | 绝不能出现 |
|---|---|---|---|
| L0 只核岗 | 只核对这一条，不申请 | 岗位链接、两句事实、"不注册、不上传、不提交"、"读不到就贴 JD" | 索要简历、附件、表单、提交 |
| L1 本地草稿 | 只在本地写草稿 | "不访问招聘网站"、"不上传"、"不提交"、文件保存在私有目录 | 上传、官网、回执 |
| L2 官网填草稿 | 在官网填写，保存草稿 | "只填写并保存草稿"、"不上传"、"不提交"、"官网会收到已确认字段" | 上传、提交、回执 |
| L3 上传指定附件 | 只上传我列出的文件 | "只上传【文件名】到【岗位】"、"不上传其他文件"、"不提交" | 允许上传、全部附件、提交 |
| L4 提交 | 提交【N】份 | "只对【范围】的【N】份提交"、"提交前给我看最终表单"、"以官网回执为准" | 任意/全部/自动继续 |

L3、L4 依赖 L2；未选 L2 时，L3/L4 不可选。L4 不能因为"用户之前授权过"就默认勾选。表里"绝不能出现"指不能作为授权动作出现；"不提交/不上传"这类否定句是必需的，不算违规。

**落盘版复核（我读到的 T3 版本）**：四个动作已经拆成独立 radio，默认草稿不生成附件行，`upload-field` 默认隐藏，`apply-status` 跟着选项变，打印速查段也换成了新话术；`test_guide.cjs` 加了空上传、form、upload、draft 不回带文件名等负断言。这说明落盘版走的是状态模型，不是只改字符串，方向是对的。剩余问题按严重度排：① 静态帮助语仍对所有模式说"看到官网回执"；② check 模式仍可能把"附件目录"带进只核岗话术；③ `intake-and-privacy.md:3` 的默认顺序仍会诱导 Agent 先要简历；④ PDF、01、仓库版先看这里仍是旧授权面；⑤ 包内 guide 仍没有行为测试。这五条不要求本轮全修，但版本说明要逐条写清"修了/没修/为什么"。如果 Codex 在我写完后继续改了这几处，以最终 `IMPLEMENTATION_NOTES.md` 为准；这一段的判断只针对我读到的版本。

### 2.2 T1：首屏顺序修得了观感，修不了"下载了用不了"

1. **首屏的"下载"还不是"加载"。** 现稿第 7 行说"解压后按先看这里把技能装进兼容的 Agent"，第 9 行就是可复制的首用指令。一个读者很可能先复制、后安装；Agent 没加载技能，就会给一个泛泛的答案，读者据此判断"没用"。第 1 轮把"下载成功，第一句却发不出去"列为第 2 号问题，T1 不能在首屏把它重新造出来。建议在指令上方加一行可验证的加载确认，直接用 `guide.html:139` 的 `installPrompt()`：请 Agent 报出实际加载的 `SKILL.md` 路径，并说明当前能完成哪些操作、缺少什么工具。这句不需要新写，且能当场暴露"没装好"。
2. **支付块要整体搬，不能只搬二维码。** 现稿第 17–27 行是完整的商业块，第 7 行还有"模型使用费另计"，第 19 行有"同一套技能/不含人工代投"。如果只把二维码下移，首屏仍出现"一次性 ¥19.9"，等于没搬。要搬的是：支持档价格、同版同权、二维码、商品链接、模型费用、无代投/无录用保证。"需自备兼容 Agent"不要跟着搬——它是使用前提，应贴着免费入口；现稿把它放在第 7 行，是对的，别在后续整理时并进支付段。
3. **首屏链接指向旧包，承诺与交付错位。** 现稿第 7 行链接 `downloads/entry-level-job-application-with-guide.zip`；按 `evaluation/search-quality-artifacts.json` 的记录，这个包是 24 个文件、363,554 字节、SHA-256 `34ca8520...` 的旧版，里面的教程仍会授权上传（`IMPLEMENTATION_NOTES.md:9` 已经诚实写明）。也就是说，首屏说"只核岗位、不上传"，点进去的教程却可能生成上传授权。三种处理，必须选一种并写进版本说明：
   - 本轮首屏先指向已修的 `docs/starter-kit/guide.html` 和技能源码，ZIP 链接标注"在售包待替换"；
   - 或者等候选包验证通过后，按发布顺序先替换 `downloads/`，再改 README；
   - 或者两者都保留，但首屏明说"GitHub 源码已修，平台在售包仍是旧版"。
   不能既不换包，又让首屏看起来已经修好。
4. **README 自己留的"补丁句"必须删。** 现稿第 37 行："如果教程生成的话里包含上传授权，改用这句……"；英文第 40 行同样。这句话在 T3 完成前是诚实的临时说明，在 T3 完成后就是自相矛盾：首屏承诺"不上传"，教程段却告诉用户"教程可能授权上传"。发版前必须删；如果 T3 没完成，就不能发版。这句话也说明 T1 和 T3 的落盘顺序会直接影响 README 的真假，版本说明里要写清"README 的哪一段依赖 T3"。

### 2.3 T2：图不是海报，是证据

1. **"左/右"与"手机可读"仍有张力。** 落盘图是 1080×1920 双栏，信息完整、字号也够；但 README 以 360 宽显示时，每栏约 180px，正文会偏小。建议再加一张 390 宽竖排（A 上 B 下）供手机直接看，或在 README 里给"点开原图"的链接；两栏图保留给桌面和 SkillPay。
2. **不得把"毕业年份未作限制"写成"2025 届可投"。** 落盘图写的是"岗位未限毕业年份，可先问是否接受 2025 届"，这是对的；这条作为后续改图的红线保留。`tests/scenarios/quick-search.md:20` 的原话是"毕业年份未作限制"，`evaluation/forward-test.md:11` 的结论是"是否接受 2025 届仍由雇主判断"，不是"符合"。

### 2.4 包与版本管理：两方都漏了"制品同一性"

这一轮讨论把包当作"交付物"，但没有定义"哪个文件是当前版本"。现在至少有四类制品：`skills/entry-level-job-application/` 源码、`docs/starter-kit/entry-level-job-application.zip`（旧技能包）、`downloads/entry-level-job-application-with-guide.zip`（在售客户包）、`dist/` 下多个历史包；T4 再加一个候选包。候选包 `downloads/entry-level-job-application-with-guide-candidate-20261119.zip` 已经出现，但我没有解压核验；以下按任务书的验包要求评估，不替它背书。没有 `VERSION`/`CHANGELOG`，没有一张表说清谁是最新。

1. **非确定性 ZIP。** `package_skill.py:45-50` 对 `guide.html` 用 `writestr`（默认取当前时间），对其他文件用 `write`（取文件 mtime）。同一份源码构建两次，ZIP 的 SHA-256 会不同。T4 记录的 SHA 只能当"这一次构建的指纹"，不能当"候选版的版本号"。建议：版本说明里同时记录 ZIP SHA 和每个成员未压缩内容的 SHA-256；成员哈希可复现，ZIP 哈希不必强求。若要做到字节级可复现，需固定 `ZipInfo.date_time` 并排序成员，这是下一轮的事。
2. **包内 `guide.html` 与仓库文件不同字节。** `package_skill.py:30-43` 会把两个安装链接替换掉；任何"包内 guide 与源码一致"的比对都会失败。技能文件可以逐字节比（`test_delivery.py:62-63` 就是这么做的），guide 只能做语义/行为断言。版本说明要写清"guide 是构建时改写版"。
3. **构建顺序。** T3 →（PDF 再生或移除）→ T4 打包；T1/T2 可并行，但 T1 引用 T2 图片前要确认文件已落盘。若先打包后改 guide，候选包就是旧话术。记录里写构建时间、输入文件哈希、完整命令。
4. **包内 PDF 是发布阻塞项。** `guide.pdf` 是同一套话术的静态版，`package_skill.py:13` 无条件把它打进客户包；我在 `tools/` 下没有找到 PDF 生成脚本。落盘版已经在 `customer-start.txt:27` 注明"guide.pdf 仍是旧版，申请授权选项请看 guide.html"，这是诚实的；但对授权文本，标注不等于消除——用户完全可能只打开 PDF，按旧版的话术去授权。两个可接受的处理：用已有 Playwright/Chrome 对 `guide.html` 的打印段重新生成 PDF（项目已经有浏览器测试依赖）；或者本轮候选包先移除 `guide.pdf` 并在 `先看这里.txt` 注明"一页速查暂缺"。如果只能保留旧 PDF，版本说明必须把它列为"已知限制"，不能写"授权话术已全部修复"。
5. **`test_delivery.py` 是硬约束，不是障碍。** 它断言客户包成员集合精确相等（`:59`）、guide 含"这是可选教程，不是投递页面"和"查看安装方法"（`:64-66`）、`先看这里.txt` 含"会用的客户直接跳过"（`:67`）、guide 内相对链接都在包内（`:68-72`）。T3/T4 改文案、加文件、改链接时，这些断言会失败——这是好事。要在记录里写"保留了哪三句/为什么"或"同步改了哪条测试"，不能默默删断言。
6. **24 个文件的对外说法。** `TESTING.md` 和讨论都写"客户包 24 个文件"；README 没有写数字，但对外说明应统一。T3/T4 若增删文件（例如加结果图、加 PDF 源、移除 PDF），这个数字就变了；所有出现处要同步，否则版本说明和测试记录对不上。
7. **候选包的"验包"要验内容，不只验结构。** T4 目前列的是根目录、无嵌套、SHA。建议加：
   - 解压到临时目录，用可配置 root 的 `test_guide.cjs` 跑一遍默认草稿/空简历/上传/提交；
   - 对包内所有 `.html`/`.txt`/`.md` 做授权短语扫描（"允许上传""上传上述附件""先问我要""读取我的简历"），命中即失败；
   - 逐成员 SHA-256 表，与版本说明一起存档；
   - 确认包内 `先看这里.txt` 与 `docs/customer-start.txt` 同源，`docs/starter-kit/先看这里.txt` 不是另一个版本。
8. **`test_guide.cjs` 的 root 要可配置。** 现在 `:7` 硬编码 `../docs/starter-kit`，所以包内 guide 永远没被行为测试跑过。把 root 改成第四个参数或环境变量，是几行改动，但它是"源文件测试"和"交付物测试"之间的桥。没有这座桥，T4 的"验包"无法证明 T3 的修复真的进了包。
9. **候选包的命名与状态。** `...candidate-20261119.zip` 带日期不带版本；建议版本说明内部用 `v0.2.0-candidate.1` 这类标识，并明确"未发布、不得作为首屏下载链接"。在售包 `34ca8520...` 在替换前保持只读；替换后要留下旧包或其哈希，便于回滚。

## 四、分歧与最值得盯的 3 个风险

严格说，我对五项裁决没有反对；有实质分歧的是任务书的验收口径——T3 的工作量定级、T1 的验收定义、T4 的验包方式（见第一节末尾）。所以我不写"无分歧"，而是把分歧限定在"怎么验收"，并给出三个最值得盯的风险。

| # | 风险 | 为什么现在最值得盯 | 可执行的护栏 | 早期信号 |
